# TeaMall V2.0 第六阶段验收报告

> 验收日期：2026-08-15
> 验收基准：develop 分支，未提交的工作区改动（V2.0-6.1 ~ V2.0-6.5 全部小阶段，叠加在 V2.0-5 未提交改动之上）

## 1. Redis Cache 基础封装

- 统一客户端：`backend/app/services/cache.py` 单例 `redis_client` 被商品缓存、分类缓存、`token_store`（认证）、`rate_limit`（登录限流）复用；客户端新增 `socket_connect_timeout=2, socket_timeout=2`，Redis 故障时快速失败，不拖垮请求；`main.py` 的 `/api/health` 复用该客户端，删除临时新建客户端。
- 缓存 API：保留 `get_json / set_json / invalidate / invalidate_categories / invalidate_products / clear_all`（clear_all 仍仅限测试环境），新增 `delete(key)`、`exists(key)`。
- TTL：新增配置 `PRODUCT_CACHE_TTL_SECONDS`（默认 300，<=0 回退默认值并告警），替换原硬编码常量；同步更新 `config.py`、`backend/.env.example`、根目录 `.env.example`、`docker-compose.yml`（`${PRODUCT_CACHE_TTL_SECONDS:-300}`）、README、部署文档。
- 故障日志：所有 Redis 操作失败由"静默忽略"改为 `logger.warning` 记录操作类型与异常类，不记录 Key 值、Token 等敏感内容。
- 认证兼容：`auth:*` 键（`auth:refresh:*` / `auth:epoch:*` / `auth:blacklist:*` / `auth:rate:*`）键名与 fail-closed 语义完全未变，Refresh Token 回归测试全绿。

## 2. 商品缓存

- 沿用既有实现：商品详情 `cache:product:{id}`、商品列表 `cache:products:{category|all}:{kw|all}:{page}:{page_size}:{scope}`（scope=on/all），缓存内容为 API 响应 JSON（`model_dump(mode="json")`），命中后 `model_validate` 还原，结构与接口一致。
- 锁定行为（新增 10 个用例）：首次 Miss→MySQL→写 Redis（带 TTL）；二次 Hit→Redis；详情/列表命中缓存 SQL 查询次数为 0；删除键模拟过期后重新走 MySQL 并重建；商品不存在 404 不落键；非法 ID（0/-1/非数字）4xx 不落键（不实现负缓存）；管理员 `include_off_sale=true` 使用独立缓存键，公开/管理员互不影响；下架商品详情仅管理员可见且保持直查 MySQL 不缓存；购物车/订单/用户接口不产生 `cache:*` 键。

## 3. 缓存失效与一致性

- 审计结论：全部商品写路径已调用失效函数（商品增删改、SKU 替换、图片上传、分类增删改、下单扣库存、用户/Admin 取消恢复库存），业务代码零改动，以测试锁定（新增 12 个用例）。
- 覆盖：名称/价格/上下架/分类修改、分类重命名（联动分类与商品缓存）、SKU 替换、图片上传、商品删除、下单扣库存（stock 10→8）、用户取消（恢复 10）、Admin 取消（恢复 10），均验证"写成功后旧键清除 → 再查返回 MySQL 最新值并重建缓存"。
- 认证隔离：商品变更清除业务缓存后，`auth:refresh:*` 键不受影响，Refresh Token 仍可成功换发新 Access/Refresh。

## 4. Redis 故障降级

- 三层语义保持：商品/分类缓存 fail-open（GET/SET 失败回退 MySQL，业务不中断，6.1 日志生效）；Token 链路 fail-closed（登录/Refresh 在 Redis 故障时返回 503 `SERVICE_UNAVAILABLE`，不放行失效令牌）；登录限流 fail-open（Redis 故障放行，不误伤正常用户）。
- 新增 10 个用例：列表/详情 GET 失败回退 MySQL；列表/详情 SET 失败不影响返回；Redis 全挂（get/set/exists/delete/scan_iter 全失败）商品查询仍 200；分类 GET 失败回退；恢复后缓存重新建立；登录/Refresh 故障时 503；恢复后登录→刷新→登出全链路正常。

## 5. 前后端联调

- 真实 HTTP 联调（临时 uvicorn + `tea_mall_test` + Redis DB15）：**7/7 通过**——注册/登录/Refresh 换发 → 管理端建分类/商品 → 商品浏览（Miss→Redis→Hit、TTL）→ 改价（缓存失效→新值+重建）→ 上下架（公开 404/管理员可见/恢复）→ 加购/下单/取消（库存变化、缓存一致）→ 登出撤销 → 健康检查（database/redis 均 true）。
- 前端：`npm run build`（vue-tsc + vite）通过，仅既有 chunk 体积警告；`frontend/src/api/products.ts` 与 `types/product.ts` 契约未变，**前端零代码改动**。
- Redis 故障实境：冷启动验证（6.1 补充）实测 Redis 不可用时后端正常启动、商品查询回退 MySQL；容器停启实境验证由 monkeypatch 故障测试（6.4）替代并在本报告说明，未操作运行中的 Docker 容器。

## 6. Redis Key 与 TTL 设计

| 命名空间 | 用途 | TTL |
| --- | --- | --- |
| `cache:categories` | 分类列表 | 默认 300s（`PRODUCT_CACHE_TTL_SECONDS`） |
| `cache:products:{category|all}:{kw|all}:{page}:{page_size}:{scope}` | 商品列表 | 默认 300s |
| `cache:product:{id}` | 商品详情（仅上架商品落缓存） | 默认 300s |
| `auth:refresh:{sha256}` | Refresh Token 指纹 | Refresh 有效期（默认 7 天） |
| `auth:epoch:{user_id}` | 会话纪元 | 无（长期） |
| `auth:blacklist:{jti}` | Access 黑名单 | Access 剩余有效期 |
| `auth:rate:{...}` | 登录限流计数 | 限流窗口（默认 300s） |

- 业务缓存与认证命名空间严格隔离，互不扫描/互不删除；全部缓存键均带 TTL，不无限积累。

## 8. 遗留问题

- 不实现负缓存：商品不存在/非法 ID 直接回源 MySQL，防缓存穿透列为后续可选项（避免过度封装）。
- 管理员查看下架商品详情保持直查 MySQL 不缓存（避免权限相关缓存复杂度），属于既有设计。
- 冷启动操作提示（非代码缺陷）：Windows 下用 `Set-Content -Encoding UTF8` 直接生成 `.env` 会产生 BOM，导致首行键名解析失败；README 的 `Copy-Item .env.example .env` 流程不受影响。后端代码需从 `backend/` 目录启动（`.env` 相对当前目录解析），从仓库根目录运行会读取根目录 compose `.env`——README 已按 `backend/` 流程编写，未做代码层改动。
- `docs/development/roadmap.md` 仍为 V1 阶段表，未覆盖 V2.0 阶段（沿用 V2.0-5 报告遗留说明，未在最小修改原则下改动）。
- Starlette TestClient 弃用警告（httpx2，既有，非错误）；前端主 chunk 约 1.1MB 构建体积警告（既有）。
- 无 CI（既有），回归依赖人工执行 pytest。
