## 3. V2.0-3.2 用户登录与 Token

### 完成内容
- Access Token：JWT HS256，claims `{sub, type=access, jti, ver, iat, exp}`，默认 15 分钟
- Refresh Token：`secrets.token_urlsafe(32)`，Redis 仅存 SHA-256 指纹，默认 7 天，每次刷新轮换（旧指纹即删，防重放）
- 会话纪元 `auth:epoch:{user_id}`：修改密码/禁用时 +1，全部旧 Token 立即失效
- Logout：黑名单当前 access `jti`（TTL=剩余有效期）+ 删除对应 refresh；多端独立会话互不影响
- Redis 故障 fail-closed：认证链路返回 503 `SERVICE_UNAVAILABLE`，不泄露内部细节

### Token 方案
- 单 Access 7 天 → Access 15 分钟 + Refresh 7 天 + Redis 会话管理；所有 Redis 键均带 TTL，不无限积累

### Redis 变化
- 新增 `auth:refresh:{sha256}`、`auth:blacklist:{jti}`、`auth:epoch:{user_id}`；测试基座每用例清空 `auth:*`

### 前端变化
- `store/auth.ts` 保存双 token；`http.ts` 401 单飞刷新并重放原请求，刷新失败清登录态跳登录页；退出登录先调后端接口（失败也清本地）

### 测试结果
- 全量 pytest 178 passed（新增 `test_token_lifecycle.py` 12 用例）；HTTP 实测 17/17：轮换、旧 refresh 失效、logout 撤销、多端、epoch、TTL、Redis 故障 503

## 4. V2.0-3.3 用户信息与账户安全

### 完成内容
- `PUT /api/auth/me`：仅允许改 `nickname`/`email`（邮箱唯一性排除自身、空串清空）；`extra=forbid` 拒绝 role/username/id 等越权字段
- `PUT /api/auth/me/password`：验证旧密码（400 `OLD_PASSWORD_INCORRECT`）→ 新密码强度校验 → 重新 bcrypt 哈希 → `epoch+1` 全部会话失效
- 全程无 user_id 路径参数，无越权面；响应永不含 password_hash

### 安全措施
- 用户只能修改自己；role/status/username/id 不可修改；改密后旧 access+refresh 全部失效，需重新登录

### 前端变化
- 新增个人中心页 `/profile`（requiresAuth）：资料展示、编辑昵称/邮箱、修改密码（旧密码+新密码+确认，改密成功清登录态跳登录页）；AppHeader 新增"个人中心"入口

### 测试结果
- 全量 pytest 191 passed（新增 `test_user_profile.py` 13 用例）；HTTP 实测 18 项行为全部正确

## 5. V2.0-3.4 RBAC

### 角色体系
- 维持 `user/admin` 两角色，不建 Permission 表（代码注释预留扩展）；新增主账号（`is_root`）概念作为不可剥夺的管理锚点

### 权限体系
- 集中式依赖：`get_current_user`（认证）+ `get_current_admin`（授权 403）；Router 无散落权限判断
- 迁移 0004（`users.status`）按阶段规划提前在 3.4 落地，支撑状态管理接口
- 迁移 0005（`users.is_root`）：seed 管理员标记主账号；主账号不可被任何管理员降级/禁用（400 `ROOT_PROTECTED`），操作自己仍为 400 `SELF_OPERATION_FORBIDDEN`；其他管理员之间可正常互管

### API 权限
- `GET /api/admin/users`（关键词搜索+分页）、`PATCH /api/admin/users/{id}/status`（禁用同步 epoch+1）、`PATCH /api/admin/users/{id}/role`；用户不存在 404 `USER_NOT_FOUND`，非法取值 422

### 前端权限
- 新增管理端"用户管理"页 `/admin/users`（表格+搜索+分页+禁用/启用+设为/取消管理员）；主账号行显示"主账号"标签并隐藏危险操作；AppHeader 管理员导航新增"用户管理"入口；前端权限仅控制 UI，真实边界由后端依赖强制

### 测试结果
- 全量 pytest 200 passed（新增 `test_admin_users.py` 9 用例，含主账号保护 2 用例）；HTTP 实测 18/18 + 主账号保护回归 20/20

## 6. V2.0-3.5 用户状态

### 状态设计
- `status`：`active` / `disabled`（默认 active，CHECK 约束强制）

### 认证影响
- `get_current_user` 校验 status，disabled → 401 `ACCOUNT_DISABLED`；`get_optional_current_user` 将 disabled 视为未登录；登录校验 status → 403 `ACCOUNT_DISABLED`；Refresh 拒绝 disabled 用户
- 原则落地：Token 合法 ≠ 用户仍有效，认证必须同时校验数据库用户状态（直改库禁用的旧 token 同样被拦截）

### 前端处理
- `http.ts` 对 401 `ACCOUNT_DISABLED` 不走刷新重放，直接清登录态并提示"账号已被禁用"跳转登录页；登录页展示禁用错误

### 测试结果
- 全量 pytest 205 passed（新增 `test_user_status.py` 5 用例）；HTTP 实测 8/8：ACTIVE 正常、禁用后登录/旧 token/refresh 全拒、启用恢复、直改库禁用拦截、公开接口按游客、无越权入口
