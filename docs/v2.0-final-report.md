## 2. 第一阶段完成内容（V2.0-1 安全与启动基础）

- `JWT_SECRET` 改为必填且无默认值：缺失、<32 字节、命中已知弱值时拒绝启动；compose 删除不安全默认值，改为 `${VAR:?}` 强制要求。
- `seed.py` 管理员从 `ADMIN_USERNAME`/`ADMIN_PASSWORD` 读取，缺失、<12 位、超 72 字节、弱密码名单命中时拒绝执行；保持幂等，不打印明文。
- JWT 解析严格校验（`sub`/`exp` 必填、sub 类型与取值校验），10 种非法 token 全部 401 无 500。
- 密码按 UTF-8 字节上限（72）校验；下单事务 `SELECT ... FOR UPDATE` 防并发超卖。
- Docker healthcheck 修正（mysql TCP ping、redis 显式 `-h 127.0.0.1`）、后端迁移有限重试（20×2s）、上传 10MB 限制；测试数据库 `tea_mall_test` 与测试 Redis（DB 15）隔离。
- 验收结论：PASS。

## 3. 第二阶段完成内容（V2.0-2 数据库工程化）

## 18. 遗留问题

以下均为 P2（记录为后续优化，不阻塞交付）：

1. 仓库无 CI（GitHub Actions），回归依赖人工执行 pytest。
2. `origin/develop` 落后本地提交，GitHub 仓库未含 V2.0 阶段 5-8 内容；发布前需用户决定执行 push（红线操作）。
3. 前端主 chunk 约 1.1MB 构建体积警告，可做路由级代码分割。
4. Starlette TestClient 弃用警告（httpx2，非错误）。
5. 登录限流仅覆盖登录接口；refresh/改密等敏感操作未限流。
6. 前端 Token 存 localStorage（httpOnly cookie 方案为后续安全增强项）。
7. 不实现商品负缓存；Redis 故障时商品查询直查 MySQL。
8. Logout 依赖有效 Access Token（过期后无法撤销 Refresh Token，属既有设计契约，测试已锁定）。
9. `docker-compose.yml` 固定 `container_name`，同一主机并行运行多个 compose 项目会冲突（9.6 冷启动验证时在副本中移除后正常）。
10. `vite.config.ts` 本地开发代理指向 `localhost:8000`（仅开发配置，不随 Docker 发布）。

## 19. 后续可选优化

- 引入 GitHub Actions CI（pytest + 前端构建自动回归，含敏感信息扫描）。
- 前端路由级代码分割，降低首屏体积。
- 限流扩展至 refresh/改密等敏感操作。

- 商品负缓存与更细粒度的缓存失效。
- Logout 在 Access Token 过期场景下仍可撤销 Refresh Token。

- 商品图片接入对象存储，降低单机磁盘依赖。
- 接入真实支付网关、短信/邮箱验证、后台任务队列（Kafka/MQ 等按需引入）。
